# Журнал метеоданих (Meteo Log) — технічна документація

> Модуль: `src/storage/meteo_log.{h,cpp}`
> Платформа: ESP32-S3 (JC4827W543), 4 MB Flash, PSRAM
> Файлова система: **LittleFS**, розділ 896 КБ (`huge_app.csv`)
> Версія документа: 2 (format `METF`, in-place writes)

---

## 1. Призначення

Модуль забезпечує неперервне журналювання метеорологічних даних
(температура, **вологість**, тиск) з фіксованим інтервалом і
утриманням за замовчуванням **15 діб**. Старі дані циклічно
витісняються новими (ring buffer). Дані зберігаються одночасно у
RAM (для швидкого читання веб-графіків) та у файлі `/meteo.bin`
(енергонезалежно).

Модуль розроблено з акцентом на **мінімізацію зносу flash-пам'яті**:
кожна проба пише лише 10 байт у свій слот, замість переписування
всього файлу.

---

## 2. Конфігурація (compile-time)

Усі параметри задаються на етапі компіляції через макроси у
`meteo_log.h` (можна перевизначати через `-D` у `platformio.ini`):

| Макрос | За замовч. | Опис |
|---|---|---|
| `METEO_LOG_INTERVAL_SEC` | `300` | Інтервал між пробами, секунди (5 хв). |
| `METEO_LOG_RETENTION_DAYS` | `15` | Термін утримання, діб. |

Похідна константа:

```cpp
CAPACITY = (24 * 60 / (INTERVAL_SEC / 60)) * RETENTION_DAYS
         = (1440 / 5) * 15
         = 288 * 15
         = 4320  записів
```

---

## 3. Структури даних

### 3.1. `MeteoRecord` — один запис (10 байт)

```cpp
struct MeteoRecord {
    uint32_t time;  // Unix timestamp (UTC, секунди)
    int16_t  temp;  // temperature × 100, °C   (0x7FFF = no data)
    uint16_t hum;   // humidity    × 10,  %    (0xFFFF = no data)
    uint16_t pres;  // pressure    × 10,  hPa  (0xFFFF = no data)
} __attribute__((packed));
```

Фіксований масштаб усіх дробових величин дозволяє зберігати їх
як цілі та уникнути float у файлі. Сентінел-значення
(`0x7FFF`/`0xFFFF`) кодують відсутність даних (зокрема вологість
при використанні BMP280 замість BME280).

### 3.2. `Header` — заголовок файлу (6 байт)

```cpp
struct Header {
    uint32_t magic;     // 0x4D455446 ("METF")
    uint16_t capacity;  // очікувана ємність (= CAPACITY)
} __attribute__((packed));
```

У заголовку **свідомо немає** полів `head` та `count`: вони
реконструюються з даних під час завантаження (див. §6). Це
усуває потребу переписувати заголовок при кожній пробі та рівномірно
розподіляє знос flash.

### 3.3. Формат файлу `/meteo.bin`

```
+-----------+---------------------------+-------------------+-----+
| Header 6B | MeteoRecord[0]    10 B    | MeteoRecord[1] ... | ... |
+-----------+---------------------------+-------------------+-----+
Offset:     0                           6                   16     ...
Загальний розмір: 6 + 4320 × 10 = 43 206 байт
```

Файл **пре-алокується** один раз (при першому ініт або міграції) і
далі ніколи не змінює розмір. Кожна проба лише перезаписує свій
10-байтовий слот за сталим зміщенням:

```
slot_offset(idx) = sizeof(Header) + idx × sizeof(MeteoRecord)
                 = 6 + idx × 10
```

### 3.4. Стан у RAM

```cpp
static MeteoRecord g_ring[CAPACITY]; // 43 200 байт (статична)
static uint16_t    g_head;           // індекс найстарішого запису
static uint16_t    g_count;          // кількість збережених проб
```

## 4. Життєвий цикл запису

```
   bmeLoop()  (main loop)
        │
        │ кожні METEO_LOG_INTERVAL_SEC (300 с)
        ▼
 meteoLogAddSample(T, H, P)
        │
        ├─ time(NULL) < MIN_VALID_TIME ?  → так: return (годинник не синхронний)
        │
        ├─ індекс слота:
        │     count < CAPACITY → idx = (head + count) % CAPACITY;  count++
        │     count = CAPACITY → idx = head;                       head = (head+1) % CAPACITY
        │
        ├─ g_ring[idx] = { now, T, H, P }
        │
        └─ writeSlot(idx)              ← єдина операція запису у flash
              │
              ├─ LittleFS.open("/meteo.bin", "r+")
              ├─ seek(6 + idx×10, SeekSet)
              ├─ write(10 байт)
              └─ close()
```

Після заповнення буфера нова проба перезаписує найстарішу, `head`
просувається кільцем — реалізовано класичний FIFO-витіснювач.

## 5. Ініціалізація (`meteoLogInit`)

Викликається один раз із `setup()` після `filesystemInit()`.

```
 meteoLogInit()
   │
   ├─ initRingEmpty()              — Ramirezництво RAM-кільця до "порожньо"
   │
   ├─ load()                       — спроба завантажити файл формату "METF"
   │     ├─ success → ідемо далі
   │     └─ fail    → migrateLegacy() або визнати порожнім
   │                   └─ writeFullFile()  ← (пере)створює файл повним
   │
   └─ reconstructIndex()           — відновити head/count зі сканування
```

### 5.1. `load()`

Читає заголовок, перевіряє `magic == "METF"`, зчитує всі `CAPACITY`
записів у `g_ring`. Якщо файл коротший — недочитані слоти лишаються
"порожніми" (`time = 0`).

### 5.2. `migrateLegacy()`

Один раз відрізає застарілий формат (magic `"METE"`, 8-байтовий
заголовок, послідовний запис без пре-алокації). Дані зчитуються у
RAM-кільце, після чого `writeFullFile()` фізично переписує файл у
новому форматі. Це автоматичне й безпечне: користувач не втрачає
історію при оновленні прошивки.

### 5.3. `writeFullFile()`

Повне переписування файлу. Викликається **лише** під час init або
міграції (ніколи — для звичайної проби). Одинична вартість:
≈ 43 КБ запису, після чого зношування розподіляється по всіх блоках.

## 6. Реконструкція індексів (`reconstructIndex`)

Щоб не зберігати `head`/`count` у файлі (що вимагало б перепису
заголовку щоразу), стан кільця виводиться з самих даних:

```
сканувати всі CAPACITY записів:
  - визначити maxTime / позицію newest
  - зафіксувати anyEmpty = (є хоча б один слот з time < MIN_VALID_TIME)

if (немає жодного валідного запису):
    head = 0, count = 0                              // порожній буфер

elif (anyEmpty == true):
    head = 0
    count = кількість записів з time >= MIN_VALID_TIME  // буфер ще не повний

else:  // буфер повний, кільце обгорнуло
    head  = (newest + 1) % CAPACITY
    count = CAPACITY
```

**Обґрунтування інваріантів:**

- До заповнення буфера записи завжди йдуть підряд зі слоту 0:
  `0, 1, 2, ..., count-1`, отже `head == 0`.
- Після заповнення нова проба йде у слот `head`, який просувається
  на 1. Найновіший запис завжди стоїть безпосередньо перед
  найстарішим: `newest == (head - 1 + CAPACITY) % CAPACITY`.

Час сканування 4320 записів у RAM на ESP32-S3 — кілька мілісекунд,
що не помітно при старті.

## 7. Аналіз зносу flash-пам'яті

### 7.1. Порівняння підходів

| Параметр | Старий (full-rewrite) | Новий (in-place slot) |
|---|---|---|
| Байт запису на пробу | 43 206 | **10** |
| Стирань блоків/проба | ~22 (11 даних + 11 метаданих) | ~2–4 |
| Стирань блоків/добу (288 проб) | ~6 336 | ~600–1 100 |
| Мінімальний ресурс flash | **~1 рік** | **~10+ років** |

### 7.2. Розподіл зносу

`/meteo.bin` займає ≈ 11 логічних блоків по 4 КБ (блок 0 містить
заголовок + слоти 0..408, блоки 1..10 — ≈ 410 слотів кожен).

Протягом 15-денного циклу кожен слот перезаписується рівно один
раз → кожен блок зазнає ≈ 410 стирань за 15 діб = **≈ 27
стирань/блок/добу**.

При номінальному ресурсі ESP32 flash ≈ 100 000 циклів стирання на
блок:
```
100 000 / 27 ≈ 3 700 діб ≈ 10 років
```

Окрім того, LittleFS виконує wear-leveling, тож логічні блоки
відображаються на різні фізичні — фактичний ресурс може бути ще
більшим.

### 7.3. Блок 0 — окрема увага

У старій реалізації заголовок переписувався кожні 5 хвилин, що
концентрувало знос на блоці 0 (1 рік до відмови). У новій версії
заголовок **взагалі не змінюється** після init — отже блок 0
зношується нарівні з іншими.

## 8. Спожиття ресурсів

| Ресурс | Значення | Примітка |
|---|---|---|
| RAM (статично) | 43 200 + ~16 Б | `g_ring` + службові змінні |
| Flash (файл) | 43 206 Б | `/meteo.bin` |
| Share LittleFS | 43 КБ / 896 КБ ≈ **4.8 %** | решта — веб-файли (44 КБ) та запас |
| Час init | 50–150 мс | читання 43 КБ + сканування |
| Час додання проби | 5–20 мс | один in-place write |

PSRAM не використовується модулем (у цьому немає потреби — 43 КБ
вільно поміщаються у внутрішній SRAM).

## 9. Публічний API

Усі оголошені у `meteo_log.h`:

| Функція | Призначення |
|---|---|
| `bool meteoLogInit()` | Монтування/завантаження логу. Викликати після `filesystemInit()`. |
| `void meteoLogAddSample(float T, float H, float P)` | Додати пробу. Ігнорується, якщо `time(NULL) < MIN_VALID_TIME`. `NaN` кодуються як сентінел. |
| `uint16_t meteoLogCount()` | Поточна кількість збережених проб. |
| `uint16_t meteoLogCapacity()` | Максимальна ємність (4320). |
| `uint16_t meteoLogSerializeJson(String&, uint16_t maxPoints=600, uint32_t from=0, uint32_t to=0)` | Компактна серіалізація з децимацією для графіків. |

Формат JSON-відповіді (див. §11).

## 10. Крайові випадки та відмовостійкість

| Ситуація | Поведінка |
|---|---|
| Перший старт (файлу немає) | `writeFullFile()` створює порожній лог; `head=0, count=0`. |
| Застарілий формат `"METE"` | Автоматична міграція через `migrateLegacy()`, без втрати даних. |
| Пошкоджений `magic` / файл | `load()` та `migrateLegacy()` повертають `false` → файл створюється наново. |
| Файл коротший за очікуваний | Недочитані слоти лишаються "порожніми"; `reconstructIndex` це врахує. |
| Годинник не синхронний | Проба пропускається (`time < MIN_VALID_TIME`). |
| Відказ датчика (`NaN`) | Значення кодуються сентінелами `0x7FFF`/`0xFFFF`, проба все одно пишеться. |
| Вимкнення живлення під час проби | LittleFS атомарний на рівні блоку: запис або виконається, або ні. Втрачається **≤1 проба**. |
| Вимкнення під час init/міграції | Можлива втрата даних (рідкісний випадок, лише при оновленні прошивки). |

### 10.1. Граничний випадок "дірка" у буфері

У нормальній роботі записи йдуть послідовно (до заповнення) або
циклічно (після), тож "дірки" (`time=0` серед валідних записів)
неможливі. Якщо вони все ж виникнуть (наприклад, після ручного
редагування файлу), `reconstructIndex`:
- виявить `anyEmpty = true`,
- припише `head=0` і `count = <число валідних проб>`.

Серіалізація може показати пробу в "отворі" як порожню — це
косметичний ефект, а не пошкодження даних.

## 11. Формат JSON-виводу `meteoLogSerializeJson`

```json
{
  "count":    4320,
  "shown":    600,
  "interval": 300,
  "capacity": 4320,
  "time": [1700000000, 1700000300, ...],
  "temp": [21.45, 21.50, null, ...],
  "hum":  [48.3,  48.1,  null, ...],
  "pres": [1013.2, 1013.4, ...]
}
```

- `count` — кількість проб у вікні `[from, to]` після фільтрації;
- `shown` — фактична кількість елементів у масивах (після децимації до `maxPoints`);
- `null` у `temp`/`hum`/`pres` — сентінел "немає даних" (наприклад, вологість з BMP280).

Децимація: `step = ceil(n / maxPoints)`; з масиву береться кожен
`step`-й елемент. Для веб-графіка типовий `maxPoints = 600`.

## 12. Конкурентність

| Потік | Операція |
|---|---|
| Main loop (core 1) | `meteoLogAddSample()` раз на 5 хв |
| Async TCP (web server) | `meteoLogSerializeJson()` за запитом |

`meteoLogAddSample` — єдиний письменник. `meteoLogSerializeJson`
зчитує снапшот `g_head`/`g_count` на початку і далі працює з RAM.
Перетин читач/письменник можливий із AsyncWebServer, але максимум
впливає на одну пробу (зсув у графіку), що явно задокументовано як
припустиме.

Прямого блокування немає навмисно: для метеоданих з 5-хв інтервалом
консистентність транзакцій не потрібна, а блокування ускладнило б
код і додало б ризик дедлоків.

## 13. Сценарій масштабування (за потреби)

Якщо знадобиться довший термін утримання або частіший інтервал:

```ini
build_flags =
    -DMETEO_LOG_INTERVAL_SEC=120     ; 2 хв замість 5
    -DMETEO_LOG_RETENTION_DAYS=30    ; 30 діб замість 15
```

При цьому:
```
CAPACITY = (1440/2) × 30 = 21 600 записів
RAM  = 216 000 Б  ≈ 211 КБ  ← все ще поміщається у SRAM (512 КБ)
File = 216 006 Б  ≈ 211 КБ  ← поміщається у LittleFS (896 КБ)
```

Граничне значення для поточного розміру LittleFS — близько
`85 000` записів (≈ 830 КБ) — далі варто або розширювати розділ
(інша partition table), або переходити на PSRAM-буферизований режим.

## 14. Діагностика (Serial)

Під час роботи модуль виводить у послідовний порт (115200 бод):

```
MeteoLog: migrating 1234 records from legacy format
MeteoLog: wrote full file (43206 B) in 87 ms
MeteoLog: capacity=4320 count=1234 head=0
MeteoLog: failed to open file for writing         ← помилка: місце/LittleFS
```

Рекомендується перевіряти лог після:
1. Першего старту з новою прошивкою.
2. Тривалої експлуатації (на відмови flash).
3. Несправностей датчика (проби пропускаються mовчки — дивитись `meteoLogCount()`).

## 15. Короткі підсумки для розробника

1. **Запис = 10 байт** у сталий слот, не переписує весь файл.
2. **Індекси не persisted** — реконструкція з timestamp's на старті.
3. **MAGIC = `"METF"`** (новий формат); старий `"METE"` мігрує автоматично.
4. **Пре-алокація** файлу до повного розміру виконується один раз.
5. **Сентінели** `0x7FFF`/`0xFFFF` кодують відсутність даних.
6. **`MIN_VALID_TIME = 1700000000`** (листопад 2023) — поріг "годинник синхронний".
7. **Wear leveling**: ~10+ років ресурсу замість ~1 року раніше.
8. **API не змінився** — заміна реалізації прозора для всіх callers.
